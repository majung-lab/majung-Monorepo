# 공통 규칙

모든 API에 공통으로 적용되는 규칙입니다.

## 기본 정보

| 항목 | 값 |
|---|---|
| 서버 주소 (PC에서 직접) | `http://localhost:4000` |
| 웹 개발 서버를 거칠 때 | `http://localhost:5173/api/...`, `ws://localhost:5173/ws/...` (Vite가 4000번으로 전달) |
| 안드로이드 에뮬레이터에서 | `http://10.0.2.2:4000` |
| 요청·응답 형식 | JSON (`Content-Type: application/json`) |
| 문자 인코딩 | UTF-8 |

- 요청 본문이 있는 API(`POST`, `PATCH`, `DELETE`)는 반드시 `Content-Type: application/json` 헤더를 보내야 합니다. **`DELETE`도 본문이 필요합니다.**
- 요청 본문에 **정의되지 않은 필드가 있으면 400 에러**가 납니다. 서버가 모르는 필드를 조용히 무시하지 않습니다.
- 타입을 자동으로 변환하지 않습니다. `version`을 `"3"`처럼 문자열로 보내면 400 에러가 납니다.

## 토큰과 권한

별도의 로그인이나 `Authorization` 헤더가 없습니다. 대신 **URL에 들어가는 토큰이 권한 역할**을 합니다.

| 값 | 발급 시점 | 가진 사람 | 할 수 있는 것 |
|---|---|---|---|
| `driverToken` | 방문 생성 응답 | 차량 앱만 | 운전자 역할로 방문 조회·변경 |
| `passengerToken` | 방문 생성 응답 | 동승자 (QR 링크로 전달) | 동승자 역할로 방문 조회·변경 |
| `driverDeviceId` | 차량 앱이 직접 만듦 | 차량 앱만 | 그 기기의 방문 기록 조회 |

- 토큰은 32바이트 랜덤 값(base64url)이라 추측할 수 없습니다. **방문 ID(`visit.id`)만으로는 아무것도 할 수 없습니다.**
- 같은 API라도 **어떤 토큰으로 호출했는지에 따라 운전자인지 동승자인지 결정**되고, 응답의 `role` 필드에 그 역할이 나옵니다.
- 동승자 웹 링크 형식은 `<웹 주소>/v/<passengerToken>`입니다. 차량 앱이 이 링크를 QR로 보여 줍니다. `driverToken`은 밖으로 내보내면 안 됩니다.
- `driverDeviceId`는 24~128자의 추측할 수 없는 값(UUID 등)이어야 합니다. 이 값을 알면 그 기기의 방문 기록을 모두 볼 수 있으니 공유하면 안 됩니다.
- 서버는 토큰이 들어간 URL을 요청 로그에 남기지 않습니다.

### 링크 만료

- 토큰(링크)은 방문 생성 후 **24시간** 뒤에 만료됩니다. 만료 시각은 `visit.expiresAt`에 있습니다.
- 만료된 토큰으로 호출하면 **410 `LINK_EXPIRED`** 가 나옵니다. 조회, 변경, 평가, WebSocket 모두 같습니다.
- 만료된 방문도 [방문 기록 API](history.md)로는 계속 볼 수 있습니다.

## 변경 요청 규칙: `requestId`와 `version`

상태를 바꾸는 모든 요청(방문 생성 제외 PATCH·POST·DELETE)의 본문에는 다음 두 값이 반드시 들어갑니다. 방문 생성(`POST /api/visits`)에는 `requestId`만 들어갑니다.

```json
{ "requestId": "8f14e45f-ceea-4e7a-9b2d-1c0a7e3f5b21", "version": 3, "...": "..." }
```

### `requestId`: 같은 요청이 두 번 처리되지 않게 하기

- 요청마다 새로 만드는 고유 값입니다. 1~128자 문자열이고 **UUID를 권장**합니다.
- 서버 전체에서 고유해야 합니다. 방문이 달라도 같은 값을 다시 쓰면 안 됩니다.
- 네트워크 오류로 응답을 못 받았을 때는 **같은 `requestId`와 똑같은 본문으로 다시 보내면** 됩니다. 이미 처리된 요청이면 다시 처리하지 않고 성공 응답을 돌려줍니다.
  - 방문 생성은 처음 만들어진 방문과 토큰을 그대로 돌려줍니다.
  - 그 외 변경 요청은 **그 시점의 최신 상태**를 돌려줍니다.
- 이미 성공한 `requestId`를 **다른 내용**(다른 본문, 다른 API, 다른 토큰)으로 보내면 **409 `REQUEST_REUSED`** 가 납니다. 본문 필드 순서는 상관없습니다.
- 실패한 요청은 기록되지 않습니다.

### `version`: 동시 수정 충돌 막기

- 방문마다 `version` 숫자가 있습니다. 1에서 시작하고 **변경이 성공할 때마다 1씩 올라갑니다.**
- 변경 요청에는 **내가 마지막으로 본 `visit.version`** 을 담아 보냅니다.
- 그사이 다른 사람이 방문을 바꿔서 서버의 version과 다르면, 아무것도 바꾸지 않고 **409 `VERSION_CONFLICT`** 를 돌려줍니다.
- 이때 클라이언트는 최신 상태를 다시 받아서(`GET /api/visits/{token}` 또는 WebSocket 메시지) 화면을 갱신하고, 사용자가 다시 결정하게 해야 합니다. 다시 보낼 때는 새 `requestId`를 쓰세요.

### 서버가 검사하는 순서

변경 요청은 아래 순서로 검사되고, 처음 걸린 에러 하나만 응답합니다.

1. 요청 형식 (필수 값, 타입, 길이, 모르는 필드) → 400 `INVALID_REQUEST`
2. 토큰 (존재 여부, 만료) → 404 `VISIT_NOT_FOUND`, 410 `LINK_EXPIRED`
3. `requestId` 중복 → 이전 결과 반환 또는 409 `REQUEST_REUSED`
4. `version` 일치 → 409 `VERSION_CONFLICT`
5. 각 API의 규칙 (역할 권한, 진행 단계, 장소 유효성 등)

그래서 `version`이 오래됐으면 다른 문제가 있더라도 `VERSION_CONFLICT`가 먼저 나옵니다.

### 트랜잭션

- 변경 요청 하나는 하나의 DB 트랜잭션으로 처리됩니다. 중간에 실패하면 아무것도 바뀌지 않습니다.
- 변경이 성공하면 그 방문을 구독 중인 [WebSocket](realtime.md) 연결로 최신 상태가 전송됩니다.

## 응답 형식

- 방문을 조회하거나 바꾸는 API는 모두 **호출한 역할 기준의 [VisitSnapshot](models.md#visitsnapshot)** 을 돌려줍니다. 변경 후 별도로 다시 조회할 필요가 없습니다.
- 에러 응답 형식은 [errors.md](errors.md)를 참고하세요.

## 값 형식

| 종류 | 형식 | 예시 |
|---|---|---|
| ID (`facilityId`, `accessPointId`, 제안 `id`) | 숫자로만 된 **문자열**, 0으로 시작 불가, 최대 16자 | `"1"`, `"12"` |
| 방문 ID (`visit.id`) | UUID 문자열 | `"83e65daf-a17f-488c-955b-b83a8b6c2964"` |
| 시각 | ISO 8601, UTC | `"2026-10-30T08:36:44.469Z"` |
| 위도 `lat` | -90 ~ 90 | `37.5405` |
| 경도 `lng` | -180 ~ 180 | `127.2193` |

시각 값은 밀리초가 있을 수도 있고(`...44.469Z`) 없을 수도 있습니다(`...29Z`). 표준 ISO 8601 파서로 읽으면 둘 다 문제없습니다.
